# Stage 3 — Vendor Experience (Frontend)

## Stage Goal

Build the full vendor-facing dashboard: profile/portfolio/package management, lead inbox, review responses, and subscription/monetization. This is the marketplace's supply side — product.md §3.2 ("Free supply first") makes vendor onboarding friction the single most consequential UX in the whole product.

## Included Frontend Arch Phases

- **Frontend Arch Phase 5** — Vendor Onboarding & Profile Management
- **Frontend Arch Phase 6** — Vendor Leads & Reviews
- **Frontend Arch Phase 7** — Vendor Monetization (Subscription, Analytics)

## Product Roadmap Cross-Reference

Maps to product.md §2.2 "Vendor goals" (all 13 points) and Product Phases 2 (Marketplace Supply), 4 (Lead Engine — vendor-facing half), 5 (Monetization).

There is no allowed-transitions state machine on the backend (confirmed by reading `lead.service.ts` — product.md's lifecycle is "a suggested progression, not a strict finite-state machine") — the only real rule is a terminal-status lock (`WON/LOST/SPAM/CLOSED` cannot transition to a different status once reached). The UI disables the status control once a lead is terminal, rather than inventing an allowed-transitions map the backend doesn't enforce

Confirmed the vendor's own review list reuses the exact same public `GET /vendors/:vendorId/reviews` endpoint (APPROVED-only) the couple-facing profile page already calls — there is no separate "all statuses" vendor-scoped review endpoint, so a PENDING/FLAGGED/HIDDEN review is invisible to the vendor too, same as to a couple

### Backend additions required for Frontend Arch Phase 5 (see `../docs/11-progress-log.md`'s 2026-09-02 addendum)
- `VendorProfile.logoMediaId`/`coverMediaId` were unwritable (absent from `upsertProfileSchema`) and unresolvable on read (`VENDOR_FULL_INCLUDE` never joined the related `Media` rows) — both fixed: the two fields are now writable on `PUT /vendors/me/profile` (validated server-side against the vendor's own READY media) and readable everywhere a full vendor is returned. This also closes [Open Question 7](10-risks-and-open-questions.md#7-vendor-detail-endpoint-cannot-resolve-the-vendors-logocover-image)'s album-cover-fallback workaround from Stage 2 — the couple-facing vendor page can now resolve a real logo/cover once a vendor sets one, though that page's own rendering wasn't changed in this pass.
- `GET /categories`/`GET /categories/:slug` now embed each category's active `services` (both the list and single-category repository functions — the list one was missed in the first pass and caused a real live 500, caught during manual verification before Playwright, see progress log) — there was no services-listing endpoint at all before this, needed for the profile editor's "services offered" checkboxes.
- A separate, unrelated worker crash was found and fixed while verifying the portfolio upload flow live: see the standalone commit "Fix notification-delivery worker crashing when a Notification row is deleted mid-flight" — not a Phase 5 feature, but blocked reliable verification of it.

### Backend/tooling changes made during Frontend Arch Phase 6
- No new backend endpoints were needed — `/leads/*` and `/reviews/:id/respond` already existed with exactly the shapes required (confirmed via a dedicated research pass before building anything, then re-confirmed field-by-field via live curl calls against a real seeded vendor/lead/review before writing any Playwright).
- `wedhub-backend/src/common/middleware/rate-limit.middleware.ts`'s four dev-friction-prone limiters (login, register, enquiry, review) were made env-configurable (`LOGIN_RATE_LIMIT_MAX`, `REGISTER_RATE_LIMIT_MAX`, `ENQUIRY_RATE_LIMIT_MAX`, `REVIEW_RATE_LIMIT_MAX`), defaulting to the original production values (10/20/10/5) when unset. The dev `.env` sets all four to 1000. This was a real, recurring problem across this entire engagement — the backend's real in-memory rate limiters (documented since Frontend Arch Phase 1) repeatedly tripped mid-Playwright-debugging and blocked verification, previously worked around only by waiting out the window or restarting the backend process. This is a permanent fix to that friction, not a one-off workaround; production behavior is unchanged since the env vars are unset outside dev.

Verified via headed Playwright (`e2e/phase-05-vendor-profile.spec.ts`, 3/3 passing).
- A vendor sees real leads arrive (test by creating an enquiry from the couple app in Stage 2 against the same vendor) and can change lead status, with the change reflected on reload (not just optimistic client state). **✅ Frontend Arch Phase 6, verified 2026-09-02** — a real couple account submitted a real enquiry against an APPROVED vendor via `POST /enquiries/single-vendor`, the resulting lead appeared on `/vendor/leads` via `GET /leads`, and a real status change (NEW → CONTACTED) via `PATCH /leads/:id/status` was reflected in both the detail panel and the list row. Verified via headed Playwright (`e2e/phase-06-vendor-leads-reviews.spec.ts`).
- A vendor can view and respond to a real review. **✅ Frontend Arch Phase 6, verified 2026-09-02** — a real APPROVED review (with `verifiedInteraction: true`, since the reviewing couple had a real lead with the vendor) rendered on `/vendor/reviews` with a correct average+per-star summary, and a real reply via `POST /reviews/:id/respond` appeared immediately without reload.
- A vendor can view real plan options, initiate a real Razorpay upgrade flow against a test/sandbox key, and see their subscription status update after a successful payment (or a realistic failure path if using test failure cards). *(Frontend Arch Phase 7 — not yet built.)*
- No plan price, feature limit, or subscription status is hardcoded anywhere in vendor-app code — verified by grep, not just by memory. *(Not yet applicable — no plan/subscription UI exists yet; Frontend Arch Phase 7 scope.)*

## Dependencies / Sequencing

Requires Stage 1 (Foundation) complete. Frontend Arch Phase 5 → 6 → 7 is the natural dependency order (a vendor needs a profile before leads make sense; leads before "did this convert" analytics make sense). No dependency on Stage 2 (Couple Experience) — the two stages can be built in either order or interleaved, per `00-index.md`'s recommended build order. Stage 3 does, however, benefit from Stage 2 existing for end-to-end manual testing (an enquiry needs to originate from somewhere) — sequence pragmatically if both are being worked by the same person, but there is no hard technical dependency either direction.
