## Task Checklist

### HIGH priority

- [x] **No client-side image compression/resize before upload** — confirmed zero uses of `browser-image-compression`, canvas-resize, or any similar technique anywhere in the frontend. Every upload flow (vendor logo/cover/portfolio/gallery, wedding-website gallery/cover, admin media) sends the original, often 10–20MB phone photo straight to the presigned-URL flow. **Fixed (2026-09-05):** new dependency-free `lib/media/compress-image.ts` (`compressImageIfPossible`) resizes to a max 2560px dimension via `createImageBitmap`/`<canvas>`, re-encodes to WebP (falls back to JPEG if the browser can't encode WebP, and always falls back to the original file untouched on any error — never a hard requirement for upload to proceed). Wired into the presign call of all 9 upload surfaces found in the codebase. Backend validation untouched, as instructed.
- [x] **Unbounded upload concurrency** — `PortfolioManager.tsx`'s `handleFilesSelected` fires `void uploadOneFile(file)` per selected file with no batching/concurrency limiter; a large multi-select gallery upload saturates the browser's connection pool and the presigned-URL issuance endpoint simultaneously. **Fixed (2026-09-05):** new shared `lib/utils/concurrency.ts` (`runWithConcurrencyLimit`) caps concurrent uploads at 3; wired into `PortfolioManager.tsx` and `ReviewForm.tsx` (the only 2 of the 9 upload surfaces that actually had unbounded concurrency — the other 7 are single-file or already-sequential loops, so this fix was scoped to where the bug actually exists rather than applied uniformly).
- [x] **No retry/remove affordance on a failed upload** — once an item's `progress` state becomes `"error"` in `PortfolioManager.tsx`, it renders only a static error message with no button; there is no retry or remove handler in the file at all (confirmed via grep — zero matches). One bad file currently has no graceful recovery path short of re-selecting it from scratch. **Fixed (2026-09-05):** `PortfolioManager.tsx`'s error tile now has Retry (re-invokes `uploadOneFile` for that file) and Remove buttons. `ReviewForm.tsx` was similarly reworked from an all-or-nothing `Promise.all` (one bad photo previously discarded every already-uploaded photo's mediaId) to per-photo status tracking with its own Retry/Remove UI and partial-success submission.
- [x] **Public data (categories/locations/featured-listings) is uncacheable** — root cause: `lib/api/client.ts`'s `apiFetch` calls `headers()` unconditionally on every invocation (used for an `X-Forwarded-For` relay), which per Next.js's dynamic-API rules forces every calling route out of static rendering — even calls made with `skipAuth: true` for genuinely public, slow-changing data. **Fixed (2026-09-05):** confirmed via grep that `search.routes.ts` is the ONLY route among all `skipAuth: true` callers with an IP-keyed rate limiter — every other public read (categories, locations, featured-listings, popular searches, featured vendors/wedding-stories/gallery/blog, SEO pages/combinations, subscription plans, wedding-website templates/published/slugs, `getVendorBySlug`/albums/reviews) hits an unrate-limited route, so relaying the visitor's IP served no purpose for them. Added a `public?: boolean` flag to `apiFetch`, independent of `skipAuth` — `searchVendors` is `skipAuth: true` but IS rate-limited, so it deliberately keeps the relay and was left untouched (also not cacheable anyway, given free-text query params). `headers()` is now skipped when `public: true`, and `next: { revalidate: 300 }` (admin-curated homepage content) or `next: { revalidate: 3600 }` (near-static reference data) was added to each. No backend change was needed — decided by rate-limiter presence, not by `skipAuth`. Left `vendor-store.ts`'s public storefront reads (`fetchPublicStore`/`fetchPublicStoreItems`) untouched — they already have an explicit `cache: "no-store"`, a prior deliberate choice (live stock/pricing) not overridden here. Also left `getWeddingWebsitePreview` untouched — a one-off preview-token link, not slow-changing catalog data.

### MEDIUM priority

- [x] **Homepage's featured-vendor-card fetch is an avoidable sequential 2-hop** — `app/(public)/page.tsx`'s `getFeaturedVendorCards()` awaits `listFeaturedListings` first, then fans out `searchVendors` per listing (the fan-out itself is `Promise.all`'d, but only starts after the first call resolves) — a real sequential dependency in an otherwise well-parallelized page, caused by `featured-listings` only returning `{id, businessName, slug}` and needing a search-based workaround to get full card data. **Fixed (2026-09-05), backend + frontend:** `featured-listing.repository.ts`'s `VENDOR_SUMMARY_INCLUDE` now also joins `vendor.profile` (shortDescription/startingPrice/currency/logoMedia); `featured-listing.service.ts`'s `listActiveFeaturedListings` maps that into the same flat public-card shape `search.service.ts` already uses, resolving the logo URL via `getPublicUrl`. Frontend's `FeaturedListing` type widened to match. `app/(public)/page.tsx` no longer has `getFeaturedVendorCards()` at all — it calls `listFeaturedListings` directly with no second hop.
- [x] **Homepage has no Suspense/streaming boundaries** — all ~7 homepage fetches sit in one top-level `Promise.all`; nothing is wrapped in `<Suspense>`. Below-the-fold, non-critical sections (wedding stories, blog, gallery inspiration) currently block the entire page's initial HTML even though they're not above-the-fold content. **Fixed (2026-09-05):** confirmed via grep this was the first `<Suspense>` usage anywhere in the codebase. `HomePage` now only awaits categories/session/popular-searches (all above-the-fold) at the top level; wedding stories, blog, gallery, and featured vendors are each their own async Server Component, wrapped in `<Suspense>` at their existing JSX position with a skeleton fallback (or `null` for the two sections with an existing hide-when-empty convention, to avoid a skeleton-then-vanish flash). Not verified against a live dev server (none running in this environment) — confirmed via a static read that this matches the documented Next.js 16 streaming pattern (`node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md`).
- [x] **Wedding-website gallery grid over-fetches image size** — `WeddingWebsiteRenderer.tsx`'s gallery mapping prefers `optimizedObjectKey` (medium/800px) over `thumbnailObjectKey` (300px) for `aspect-square` grid cells that only need ~300px — roughly 5x the necessary bytes per photo. Bounded in severity by the 30-photo cap (see "moot" note above), but still a real, fixable inefficiency. **Fixed (2026-09-05):** added a `gridThumbnailKeyFor` helper (thumbnail-first, falling back to optimized/original) used only by the gallery grid cell; the hero cover photo and couple photo (genuinely larger displays) keep the existing `objectKeyFor` (optimized-first). Confirmed via grep this is now consistent with every other thumbnail-grid usage already in the codebase (portfolio manager, admin review photos, vendor detail page, admin featured-media board all already preferred `thumbnailObjectKey` first) — this file was the sole outlier.
- [ ] **No lightbox/full-screen gallery view exists for wedding websites** — clicking a gallery photo in `WeddingWebsiteRenderer.tsx` currently does nothing (no modal, no expanded state, no click handler). The review doc's concern about "large variant vs. grid variant" selection is moot until this is built, since there's no full-screen consumer yet. Not a regression — a genuinely unbuilt feature. If/when built, wire it to the `large`/`optimizedObjectKey` variant, not the grid's thumbnail (see the backend task list's "orphaned large variant" item — building a lightbox may be the actual justification for persisting that variant instead of discarding it).
- [x] **Frontend error handling collapses all failure modes into one shape** — `lib/api/client.ts`'s `apiFetch` throws a single `ApiRequestError` class for every HTTP failure; a raw network failure (`fetch` throwing `TypeError`) is never caught/wrapped and propagates as an unrelated exception type. No call site can currently distinguish network vs. validation vs. auth vs. server errors without manually inspecting `.status`/`.code` each time. **Fixed (2026-09-05), scoped to the confirmed real gap:** added a new `ApiNetworkError` class (`lib/api/types.ts`) — thrown when `fetch` itself rejects (offline/DNS/CORS) or `response.json()` fails to parse, both now wrapped in `apiFetch`. Left `ApiRequestError` itself untouched (no validation/auth/server sub-classing) since confirmed via grep that all 17 existing consumers already correctly discriminate via `error instanceof ApiRequestError && error.status === ...` — splitting that single class into several would break/require-updating every one of those call sites for no behavioral gain; `.status`/`.code` already give them everything they need. The one real, confirmed gap (network failures escaping unwrapped) is fixed; `ApiRequestError`'s existing shape/behavior is unchanged, so none of the 17 call sites needed updating.

## Implementation order (adjusted from the review doc's own §30 phase structure)

The review doc's own "Phase 1: critical security" phase is **dropped** — independently confirmed already solid. Suggested frontend order:

1. Image/media upload performance (compression, concurrency limiting, retry/remove) — the most user-visible fix, touches every upload surface but each surface's fix is small and mechanical once the shared pattern exists
2. Public-data caching fix, coordinated with the backend task list's cross-referenced item
3. Homepage: featured-vendor-card sequential-fetch fix (coordinate with backend) + Suspense boundaries for non-critical sections
4. Wedding-website gallery variant selection (thumbnail vs. medium) — small, independent, no dependency on the lightbox item
5. Typed error classes in `apiFetch`
6. Large Client Component refactors — lowest urgency, pick off one at a time opportunistically, never as a big-bang rewrite
