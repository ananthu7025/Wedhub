# Stage 5 — Monetization

## Stage Goal

Enable vendors to pay for and receive differentiated value (Pro/Premium plans, entitlements, optional featured placement) — without ever making basic vendor existence pay-gated (product.md §3.3: "Paid value, not paid existence").

## Included Architecture Phases

- **Arch Phase 11** — Subscription & Billing Foundation
- **Arch Phase 12** — Entitlement Enforcement
- **Arch Phase 13** — Featured Listings & Promotions

## Product Roadmap Cross-Reference

Maps to **Product Phase 5 — Monetization** (product.md §70: subscription plans, payments, billing, featured listings, coupons).

## Included Product Concerns

- Subscription model: FREE (₹0), PRO (₹5,999/mo starting), PREMIUM (₹12,999/mo starting), full feature lists per tier — all prices/limits admin-configurable, **never hardcoded** — product.md §26.
- Subscription principles and status enum: `TRIALING/ACTIVE/PAST_DUE/PAUSED/CANCELLED/EXPIRED` — product.md §27.
- **All 8 subscription scenario walkthroughs (product.md §28)** — treat each as an acceptance-test narrative:
  - **A — Free vendor**: registers, admin approves, on FREE, visible, no payment required.
  - **B — Upgrade**: plan → billing period → coupon → payment intent → payment flow → webhook verified → `ACTIVE` → entitlements updated → invoice stored → vendor confirmed.
  - **C — Payment succeeds but browser closes**: webhook is the source of truth, not frontend callback; subscription still activates.
  - **D — Webhook arrives twice**: idempotency key detected, second event ignored safely, no duplicate subscription/invoice.
  - **E — Payment fails**: `PAST_DUE`, notification sent, grace period configurable, entitlements removed after grace period, vendor falls back to FREE (profile does not disappear).
  - **F — Vendor cancels**: configurable immediate vs. `cancel_at_period_end` (recommended default: true).
  - **G — Downgrade**: paid visibility/analytics restricted at period end; portfolio over the free limit is **never silently deleted** — mark excess media inactive/hidden, ask vendor to reduce, preserve for a retention period.
  - **H — Refund**: original payment stays immutable; refund is a separate record; entitlement behavior depends on refund policy.
- Billing model: payment provider abstraction (Razorpay first, Stripe-ready), entities (Payment, Subscription, Subscription Plan, Invoice, Transaction, Refund, Webhook Event, Coupon); webhooks must be signature-verified, idempotent, logged, replay-safe — product.md §29.
- Featured listings: admin-configurable category/city/placement/duration/vendor/dates/price; auto-activates/deactivates on schedule; must be clearly labeled as sponsored — product.md §30.
- Future pay-per-lead (product.md §31-32) is explicitly **out of scope** for this stage — see [`09-stage-growth-and-scale.md`](09-stage-growth-and-scale.md)'s forward-looking placeholder and [Risk 5](10-risks-and-open-questions.md#5-pay-per-lead-has-no-architecture-phase).
- Entitlements-over-plan-checks principle (Coding Rule 8, [`01-reference-cross-cutting.md`](01-reference-cross-cutting.md)) — `can("featured_listing")`, `can("advanced_analytics")`, `limit("portfolio_items")`, never `if plan === "premium"`.
- Free plan strategy: free vendors must retain search presence, profile, basic enquiries, reviews, basic portfolio, basic analytics — "do not make free vendors useless" — product.md §54.
- Revenue-stream prioritization: do not activate every revenue stream at MVP; priority order is `Free supply → traffic → enquiries → paid visibility → subscriptions → lead monetization` — product.md §55.

## Acceptance Criteria

- Admin can change plan pricing without a deployment; payment status comes only from verified provider webhook events, never a frontend callback; duplicate webhooks never duplicate a subscription or invoice; subscription state remains consistent after retries. — **Met**, verified live against Razorpay's real test-mode API (see progress log).
- All 8 lettered scenarios (A–H above) pass as explicit test scenarios, especially: idempotent webhook replay, grace-period fallback to FREE, media never silently deleted on downgrade, refund creates a separate immutable record. — **A–G fully verified live** with real Razorpay orders and correctly-HMAC-signed webhook payloads. **H (refund) is verified at the data-model level only** (the original Payment row is provably never mutated; a Refund is provably a separate record) — the live Razorpay refund API call itself could not be exercised end-to-end because it requires a payment that was genuinely processed through Razorpay's hosted checkout with a real test card/UPI instrument, which needs a frontend; a fabricated payment ID correctly gets rejected by Razorpay's real API with a 404, confirming the integration correctly fails rather than silently succeeding. Flagged explicitly rather than claimed as fully done.
- Plans/prices/limits admin-configurable, never hardcoded (Coding Rule 8); portfolio/video limits and analytics access are read through `EntitlementService` everywhere, with zero `if plan === "..."` checks in application code. — **Met**, verified live (Arch Phase 12, see progress log): `env.MEDIA_MAX_PORTFOLIO_ITEMS` — the pre-Phase-12 hardcoded global limit — was removed entirely once the plan-derived check replaced it.
- Scenario G's "never delete, mark inactive, restore on upgrade" behavior. — **Met**, verified live end-to-end through the real checkout/webhook/cancellation paths, not just direct function calls (see progress log for the exact sequence).
- Admin can configure category/city/placement/duration/vendor/dates/price for a featured listing; system correctly distinguishes a listing's admin-set `status` from whether it's actually within its date window right now; featured listings must be clearly identifiable as a distinct concept from organic results. — **Met** (thin slice), verified live (Arch Phase 13, see progress log): the public read endpoint only ever returns listings that are both `status=ACTIVE` AND within `[startDate, endDate]` right now — an `ACTIVE` listing scheduled for the future correctly does not appear. Automatic status transitions, vendor self-purchase, and actual homepage/search placement are explicitly deferred per the thin-slice scope.

## Open Questions

This stage carries the most open risk-log entries — resolve via `02-mvp-cut-line.md` rather than re-litigating here:

- **Arch Phase 8/12 MVP gap** ([Risk 1](10-risks-and-open-questions.md#1-arch-phase-812-mvp-gap)) — resolution already applied above (minimal Phase 12 in MVP).
- **Entitlements required even if Featured Listings is thinned** ([Risk 4](10-risks-and-open-questions.md#4-entitlements-still-required-even-if-featured-listings-is-thinneddeferred)) — Phase 12's portfolio/analytics gating is required at MVP regardless of Phase 13's scope; do not use Phase 13's deferral as a reason to skip Phase 12.
- **Featured Listings MVP contradiction** ([Risk 4b](10-risks-and-open-questions.md#4b-featured-listings-mvp-contradiction)) — product.md calls it MVP, architecture.md defers it; thin-slice resolution applied above.
- Payment provider: confirmed Razorpay-first with a Stripe-ready abstraction (product.md §29, architecture.md §64) — both docs agree, no conflict, just confirming for the record.
- **New judgment calls resolved during Arch Phase 11** (not pre-existing risks, decided during implementation): (1) Built on Razorpay's **Orders API** (one-time payment per billing cycle, periods tracked ourselves) rather than Razorpay's native **Subscriptions API** (which requires registering a separate set of Plan objects on Razorpay's own side and lets Razorpay drive renewal timing) — confirmed with the user. Simpler to build and verify correctly in one pass; renewal still requires a fresh checkout each period rather than an automatic recurring charge, acceptable for MVP and revisitable later. (2) "What plan is a vendor on right now" is derived from the vendor's latest `TRIALING/ACTIVE/PAST_DUE` `Subscription` row, not a denormalized column on `Vendor` — confirmed with the user, avoiding a second place that must stay in sync with status transitions (the exact class of bug Arch Phase 7/8 already hit once with index drift). (3) `EnquiryRoutingMode.CATEGORY_REQUEST`-style schema-completeness-without-an-endpoint precedent continues here: `Subscription.razorpaySubscriptionId` exists in the schema for a possible future move to the Subscriptions API, but is never populated by this phase's code.
- **A real design flaw was caught and fixed before it shipped, not left in:** the first implementation of checkout-initiation (`POST /subscriptions/me/upgrade`) created the `Subscription` row immediately — as `ACTIVE` for a paid plan — at the moment the Razorpay order was created, before any payment had happened. This directly violated product.md §28 Scenario B's own step order (`ACTIVE` is step 8, strictly after the step 7 webhook) and Scenario C's principle that the webhook is the *only* source of truth. Caught immediately during the first live verification pass (a vendor appeared "subscribed" with zero payment). Confirmed with the user and fixed at the design level, not patched: a `Payment` can now exist with no `Subscription` yet (`Payment.subscriptionId` made nullable, with `pendingVendorId`/`pendingPlanId`/`pendingCouponId` carrying the checkout's intent until payment clears); the `Subscription` row is created for the first time — always `ACTIVE` — inside the webhook's `payment.captured` handler, in one transaction with linking the payment to it. Re-verified: a fresh checkout now correctly leaves the vendor on implicit FREE (`GET /subscriptions/me` returns `null`) until the webhook fires.
- **A second real bug was caught and fixed during live webhook testing:** the webhook handler assumed a captured payment always maps to exactly one activation/renewal attempt, and crashed (500, unique-constraint violation on `invoices.payment_id`) when the same order received a second `payment.captured` event carrying a *different* Razorpay payment id than the one already recorded — surfaced by a test-script bug that generated a fresh random payment id per invocation instead of reusing the real one, but a genuine defensive gap regardless (Razorpay's own retry/edge-case behavior isn't fully documented to rule this out). Fixed by checking `payment.status === "CAPTURED"` and short-circuiting before any activation/invoice logic runs, independent of the event-id-level idempotency check. Re-verified: a second capture event against an already-captured order now correctly no-ops with a 200 and zero duplicate invoices.
- **A third real bug, unrelated to billing logic itself, was caught and fixed:** Razorpay's `receipt` field has an undocumented-until-hit 56-character server-side limit; the original `checkout-${vendorId}-${Date.now()}` format (a UUID plus prefix plus timestamp) exceeded it, and the resulting Razorpay API error serialized to the unhelpful literal string `"[object Object]"` in the error response because the global error middleware only handled native `Error` instances, not the Razorpay SDK's own `{ statusCode, error: {...} }` rejection shape. Fixed both: shortened the receipt to a short random token (the full vendor/plan IDs already travel in Razorpay's `notes` field, which has no such limit), and taught `error.middleware.ts` to JSON-stringify non-Error rejections in non-production environments so the real provider error message is visible during development instead of being swallowed.
- **New judgment calls resolved during Arch Phase 12** (confirmed with the user during implementation, not pre-existing risks): (1) The grace-period-elapsed → FREE fallback (Scenario E) and the cancel-at-period-end → FREE transition (Scenario F→G) are both evaluated **lazily, at read time**, inside `EntitlementService.getEffectivePlan()` — the first entitlement check after the deadline passes flips the `Subscription` to `EXPIRED` and runs the media sweep in the same call — rather than building a new BullMQ repeatable-job/cron subsystem. No such scheduler exists anywhere in the codebase yet (`jobs/schedules/` is an empty scaffold); building one was judged out of scope for a "minimal" Phase 12. (2) There is no separate "downgrade" endpoint — a vendor downgrading Premium/Pro → Free calls the *existing* `POST /subscriptions/me/cancel` with `immediate: false` (the already-recommended default). Downgrade and "cancel, don't renew" are the same event from the system's point of view. (3) Scenario G's "mark excess media inactive" is modeled as a new `MediaStatus.INACTIVE` enum value, deliberately kept separate from the existing `MediaModerationStatus.HIDDEN` (a moderator's trust/safety action on a different axis) — conflating the two would make a future moderation UI unable to distinguish "the vendor's plan doesn't cover this" from "a moderator rejected this," and would risk a re-upgrade wrongly un-hiding moderator-rejected content. (4) Restoring entitlement-hidden media on upgrade/trial-start/renewal (the inverse of Scenario G) was confirmed with the user as in-scope, even though product.md only states the downgrade direction explicitly — reasoned from "preserve for a retention period" implying the data was kept so it could return.
- **A genuine gap found and closed, not part of the original ask:** there was no vendor-facing analytics read endpoint at all before this phase (only write-side `AnalyticsEvent` logging from Arch Phase 7/8, and no `vendor_profile_viewed` event was ever logged from the public vendor-profile route). Confirmed with the user: built a thin `GET /vendors/me/analytics` backed by aggregate queries over the *existing* `AnalyticsEvent`/`Lead`/`Review` tables — FREE gets a 30-day window with totals only, PRO/PREMIUM get a 90-day window plus a day-by-day breakdown — gated through `canVendorAccess(vendorId, "analytics_level")`. This is intentionally not Arch Phase 18's full analytics pipeline, just enough for the `analytics_level` entitlement to have something real to enforce. The public vendor-profile route (`GET /vendors/:slug`) now logs `vendor_profile_viewed` (best-effort, matching the existing `logAnalyticsEvent` pattern) so the endpoint has real data to report.
- **Entitlement keys with no gated feature yet, by design:** `featured_eligibility`, `promotional_placement`, `response_tools`, and `priority_support` are declared in `entitlement.constants.ts`, seeded with real per-plan values, and readable via `canVendorUse()` — but nothing in the codebase gates on them yet, since Featured Listings (Arch Phase 13) doesn't exist yet and there's no backend surface for "response tools" or "priority support." Same schema-completeness-without-an-endpoint precedent as `Subscription.razorpaySubscriptionId` from Arch Phase 11 — the entitlement plumbing is ready for Arch Phase 13 to consume, not fabricated to look complete now.
- **New judgment calls resolved during Arch Phase 13** (confirmed with the user during implementation): (1) `placementType` is a real enum (`HOMEPAGE`/`CATEGORY_PAGE`/`CITY_PAGE`/`SEARCH_RESULTS`) with optional `categoryId`/`cityId` FKs, rather than architecture.md's four separate "placement types / city placement / category placement / priority" tasks becoming four disconnected fields — product.md's own example (a combined city+category campaign) is just a `CATEGORY_PAGE` listing with both FKs set. Zod-level validation enforces `categoryId` is required for `CATEGORY_PAGE` and `cityId` for `CITY_PAGE`. (2) `paymentId` is an optional, nullable, unique FK to the Arch Phase 11 `Payment` table — admin-recorded for now (e.g. after a manual/offline sale), with no new checkout flow built; a future vendor self-purchase flow can populate the same field. (3) `status` (`DRAFT/SCHEDULED/ACTIVE/EXPIRED/CANCELLED`) is entirely admin-set by hand — no scheduler flips it automatically, matching the deferred "automatic campaign activation/expiry scheduling." The public read endpoint compensates by filtering on both `status=ACTIVE` AND the date window covering "now," so a listing marked `ACTIVE` too early or left `ACTIVE` past its `endDate` still correctly never appears publicly.
- **A real bug was caught and fixed during live verification:** `Payment.id` has a unique constraint on `FeaturedListing.paymentId`, correctly enforced at the database level — but linking an already-linked payment to a second listing surfaced as a raw 500 `INTERNAL_SERVER_ERROR` with a leaked Prisma stack trace, because the service layer didn't catch the `P2002` unique-constraint violation before it reached the generic error handler. Fixed using the same `isUniqueConstraintViolation`/`ConflictError` pattern already established in `categories.service.ts` — re-verified live: the same request now correctly returns `409 CONFLICT` with a clear message instead of a stack trace.
